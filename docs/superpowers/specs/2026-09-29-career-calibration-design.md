# 职业专项分析 / 现实校准设计规格

**日期：** 2026-09-29  
**状态：** 已经用户确认产品方向，待实施计划  
**适用项目：** Jianvia `bazi-mvp`

## 1. 目标与成功标准

基础报告负责发现用户的职业倾向、隐藏优势、驱动力、工作方式与较宽的职业可能性。新的「职业专项分析 / 现实校准」负责读取这些已有结论，结合用户当前的现实边界、职业资本、价值偏好和可验证的市场证据，收窄成 3–5 个值得优先验证的职业假设。

功能验收时，用户应该能够明确回答：

1. 哪些基础报告方向在现实条件下被保留或强化；
2. 哪些方向因收入、城市、家庭责任、时间、资金或重新起步成本而降低优先级；
3. 当前最值得优先验证的 3–5 个职业方向是什么；
4. 每个方向可以如何用最低成本进行现实验证，而不是立即辞职或赌上现有现金流。

## 2. 不可突破的边界

### 2.1 四项架构硬约束

1. **单向继承。** 基础报告只由出生信息与现有基础分析逻辑生成。职业专项只能读取基础报告的结论作为「待校准的基础倾向」，不得写回、修改、覆盖或重新生成基础报告。
2. **固定分析顺序。** 专项分析内部必须依次处理：基础倾向 → 现实约束 → 职业资本 → 市场证据 → 收敛方向。提示词、服务端输入与报告 Schema 都要反映这一顺序，不把所有信息混成一段交给模型自由发挥。
3. **支付后才检索。** 现实问卷和摘要确认阶段不发起 Google Search 或招聘数据请求。只有用户确认摘要、完成现有支付验证并开始生成后，才可检索。
4. **旧生成链路彻底断开。** 旧报告可在当前标签页内只读打开，但「工作 / 行业 / 城市 / 共事 / 自定义问题」五个旧入口、旧问卷与旧生成 API 都必须从可达路径中移除。直接构造旧 URL 或旧 payload 也不能新建旧类型报告。

### 2.2 受保护范围

- 不修改出生信息输入逻辑。
- 不修改公历 / 农历换算、四柱排盘或其他排盘算法。
- 不修改现有基础报告 API、Schema 或生成主链路。
- 不修改支付提供方、凭证签名、回调验签或交易状态机的核心逻辑。
- 不引入新的前端状态管理库。
- 不为未来假设预先建设复杂基础设施。
- 工作区中用户尚未提交的 `lib/gemini/prompt.ts` 属于基础报告生成逻辑，必须原样保留，不得回滚、覆盖、格式化或随本功能提交。

## 3. 产品流程

### 3.1 新用户主路径

1. 用户根据出生信息生成基础报告。
2. 基础报告结果页只提供「开始职业专项分析」主入口。
3. `/explore` 显示简短介绍：基础报告用于发现可能性，接下来会用 2–4 分钟结合现实条件进行收窄。
4. 用户依次完成现实校准问卷。界面只显示当前阶段名称，不显示「第 4 / 27 题」。
5. 问卷完成后先进入「现实条件摘要」。用户可返回修改，也可确认继续。
6. 用户确认摘要后进入现有支付环节。
7. 支付服务端验证通过后，后台才开始招聘市场检索和职业专项生成。
8. 生成完成后进入 `/deep-report`，展示 3–5 个职业假设、暂不优先方向与 30 天验证计划。

### 3.2 旧功能处理

- 删除新流程中的方向选择页和五个方向卡片。
- 删除前端对旧固定问卷、旧自定义问题生成与旧专项生成路径的调用。
- 删除或显式拒绝 `/api/deep-analysis/custom-questions` 等只为旧流程服务的写入 API。
- `/api/deep-analysis/report` 只接受新的职业现实校准版本和完整的规范化输入；旧问卷版本、旧方向或人工构造的旧 payload 返回 400/410，不调用检索或模型。
- 支付创建接口只允许新职业专项的内部方向 ID，但不改变现有签名与交易逻辑。
- 旧 `sessionStorage` 问卷草稿通过会话版本升级失效，避免恢复到已删除的路径。
- 已生成且能被当前 Schema 解析的旧报告继续只读渲染，但不显示「再选一个旧方向」的按钮。

## 4. 问卷信息架构

问卷是「现实约束校准」，不重测性格、兴趣、MBTI 或命理倾向。题库从 JSX 中抽离为独立配置，每题包含 `id`、`section`、`type`、`question`、`options`、`required`、`maxSelections`、`condition`、`helperText` 和校验规则。

### 4.1 八个可见阶段

1. **当前状态：** 职业状态、进入新方向的时间要求。
2. **收入与现金流：** 最低月收入区间、降薪容忍度、可承受的低收入缓冲期。
3. **现实责任：** 必须持续承担的家庭、住房、照护与其他长期责任。
4. **地点边界：** 可接受的迁移范围和限制迁移的原因。
5. **转型投入：** 每周时间、最长准备期、前期资金预算。
6. **职业资本：** 经验、技能、可证明成果、重新起步容忍度、学习 / 考证 / 学历接受度。
7. **工作边界：** 不能长期接受的工作条件、可接受的收入结构和就业形式。
8. **当前优先级：** 最多选择 3 项价值偏好，V1 不实现拖拽排序。

### 4.2 条件逻辑

- 降薪容忍度为「完全不能接受」时，不显示低收入缓冲期。
- 位置必须固定或只能有限迁移时，显示迁移限制原因。
- 用户选择「暂时没有明显家庭责任」时，该选项与其他责任互斥，不追问照护细节。
- 用户选择「可以全职投入」后，不再追问兼职每周时间细分。
- 地点范围不包含海外、且候选方向不涉及国际工作时，不显示语言与海外资格题。V1 只在用户主动表示可考虑海外时追问工作语言，不询问签证或移民信息。
- 多选中的「无 / 都可以 / 暂不确定 / 几乎没有职业资本」与具体选项互斥。
- 选择「其他」时开启最多 200 字的可选或必填补充，是否必填由题目配置决定。
- 价值题最多 3 项；其他有上限的多选题在第四项尝试时给出即时可读错误，不静默失败。
- 用户返回后保留答案；上游答案导致某条件题隐藏时，提交前必须剔除该隐藏题的旧答案。

## 5. 数据模型与状态

### 5.1 客户端草稿

- 沿用当前标签页的 `sessionStorage`，不写入 URL、Cookie 或 `localStorage`。
- 升级会话版本，旧问卷草稿不恢复；旧完成报告在可解析时继续只读保留。
- 草稿保存原始问卷答案、当前阶段、当前题目、摘要确认状态、支付恢复信息和报告。
- 生成新的基础报告时，清空上一份未完成的现实校准草稿，但不修改新基础报告本身。

### 5.2 规范化服务端数据

服务端把可见问卷答案验证并转换为明确结构：

```ts
type CareerCalibration = {
  careerStatus: string;
  transitionUrgency: string;
  income: {
    minimumMonthlyIncome: string;
    salaryDropTolerance: string;
    runway?: string;
  };
  responsibilities: string[];
  responsibilityContext?: string;
  location: {
    mobility: string;
    constraints: string[];
  };
  transitionCapacity: {
    weeklyHours: string;
    preparationHorizon: string;
    maxBudget: string;
  };
  careerCapital: {
    experience: string[];
    skills: string[];
    evidence: string[];
    custom?: string;
  };
  restartTolerance: string;
  educationTolerance: string;
  workConstraints: string[];
  incomeModels: string[];
  employmentTypes: string[];
  languages?: string[];
  externalConstraints?: string[];
  values: string[];
  customContext?: string;
};
```

具体字段用 Zod 定义为服务端唯一信任边界。数值与收入用区间枚举保存，除「自定义金额」外不收集精确资产、负债或收入明细。

### 5.3 Supabase

- 沿用 `deep_report_sessions` 的 `answers jsonb`、`questionnaire_version`、`report_result`、支付和报告状态字段，不新建用户资料表。
- 正式提交与生成阶段保存规范化现实校准数据；未支付草稿只保存在当前标签页。
- 不存储原始出生信息、身份证、公司名称、家庭成员姓名、银行信息、精确资产或精确负债。

## 6. 服务端分析管道

服务端不只把一包混合 JSON 交给模型。输入被分为五个明确阶段，并保持下列单向数据流：

1. **`baseTendencies`：** 从已完成基础报告创建只读摘要，包含职业画像、隐藏优势、驱动力、工作方式、任务类型、宽职业方向、环境与消耗模式。无此输入不得启动专项生成。
2. **`hardConstraints`：** 收入、现金流、责任、城市、时间、资金、重新起步、学习 / 资格与工作禁区。这一阶段先产生保留、降级与暂不可行的边界，不让价值偏好覆盖硬约束。
3. **`careerCapital`：** 对候选方向的可迁移经验、技能、作品、客户、人脉、证书、管理经验与个人品牌进行第二层收窄。
4. **`marketEvidence`：** 仅在支付凭证验证后开始搜索。检索只使用提取后的职业候选关键词和必要的地区 / 门槛条件，不传输出生信息、家庭原始文本或不必要的隐私数据。
5. **`convergence`：** 硬约束先过滤，然后综合基础倾向、职业资本、可验证市场证据和价值偏好进行排序，得到 3–5 个职业假设。

提示词必须使用分区标签按上述顺序传入，并明确：

- 基础报告是待校准的探索假设，不是科学测评事实；
- 现实信息只用于筛选和排序，不得反向改写基础报告；
- 价值偏好只是排序器，不是硬约束；
- 招聘证据不足时降低结论强度，不编造薪资、岗位数、趋势或证书要求；
- 禁止输出「最适合」「唯一方向」「你必须」「你应该辞职」等决策替代式语气。

## 7. 市场证据接口

### 7.1 V1 真实能力

项目已有 Gemini Google Search 招聘证据链路，V1 继续复用该能力。它可以核对真实职位名称、职责、地点与部分门槛，并由服务端校验来源。

V1 不宣称已具备稳定的全市场岗位数量、平均薪资、增长率或行业趋势数据库。这些字段通过 `marketEvidence` 接口预留，未获得有效来源时标记「市场可行性待验证」。

### 7.2 搜索与报告的失败隔离

- 检索超时、无来源或来源校验失败不阻断报告。
- 报告仍然完成基础倾向、硬约束和职业资本筛选，并在相应方向显示市场证据状态。
- 只有通过现有白名单、HTTPS、职位详情页和引用文本校验的来源才能显示。
- 查询日期不冒充发布日期，搜索索引不等于职位仍可投递。

## 8. 报告数据与展示结构

职业专项报告使用明确的职业报告 Schema，不把旧深度报告的通用卡片当作主体。旧报告 Schema 仅用于只读兼容。

报告按以下顺序展示：

1. **你的现实职业边界：** 3–6 条真正改变职业选择的硬约束。
2. **你的可迁移职业资本：** 哪些经验、技能或成果不用清零，可如何用在新方向。
3. **当前值得优先验证的职业方向：** 3–5 个可搜索、可验证、粒度适中的职业假设。
4. **每个方向的现实判断：** 为什么进入候选、现实匹配、最大门槛、可迁移资产、主要风险、市场证据状态和最低成本验证。
5. **暂不建议直接进入的方向：** 0–3 个，只在存在明显的基础报告候选但当前硬约束不允许时显示。
6. **未来 30 天验证计划：** 最多 3 个动作，优先真实岗位分析、mini project、从业者访谈、少量投递或小规模接单。
7. **简短免责说明：** 本报告用于职业探索与决策辅助，不替代个人职业决策；市场、薪资和需求会随地区与时间变化。

每个职业假设使用自然语言分层，不使用 S/A/B 等级：

- 现在值得优先验证；
- 有潜力，但存在现实门槛；
- 长期可能适合，但目前不宜直接切换。

## 9. UI / UX

- 沿用现有暖中性网页设计系统、卡片、按钮、圆角、间距与字号层级，不创建全新视觉语言。
- 这是移动浏览器页面，以 375 / 390 / 430px 为主要验收宽度，同时保持桌面端正常。
- 每屏尽量只承担一个决策。选项多时使用紧凑的自适应双列；文字较长或系统字体放大时，内容区可局部滚动，底部操作仍可达。
- 所有可点击区域至少 44px。单选、多选、disabled、selected、focus、error 状态必须明确。
- 多选状态不只靠颜色，同时提供勾选符号和语义化表单控件。
- 问题标题使用 `fieldset/legend`，错误使用 `role="alert"`，动态选择反馈使用 `aria-live`，按钮和表单保持键盘可操作与可见 focus。
- 重新生成失败时不清除答案、摘要确认、支付凭证或上一份成功报告。

## 10. Loading、错误与恢复

Loading 不显示虚假百分比，只展示真实阶段：

1. 正在整理基础职业倾向；
2. 正在识别现实限制；
3. 正在评估可迁移职业资本；
4. 正在核对职业市场证据；
5. 正在收窄候选职业方向；
6. 正在生成低成本验证路径。

错误恢复规则：

- 问卷不完整时定位到第一个缺失的可见题，显示具体文案。
- AI 失败时回到生成前状态，提供「重新生成报告」，不重复支付且不丢失答案。
- 市场检索失败不视为整份报告失败；只将市场状态降级为待验证。
- 报告页刷新优先从当前会话恢复已完成报告，不重新调用检索或模型。
- 会话损坏、版本不兼容或缺少基础报告时安全返回基础报告入口，不尝试补造数据。

## 11. 埋点与隐私

项目当前没有已接入的产品分析平台。V1 提供类型化的埋点适配器与无存储默认实现，调用以下事件，但不上传原始自由文本：

- `career_calibration_started`
- `career_question_answered`
- `career_calibration_completed`
- `career_summary_confirmed`
- `career_report_generation_started`
- `career_report_generated`

只传递问题 ID、阶段、是否跳过与耗时等最小元数据。收入、家庭责任、城市、职业经历和自由文本不作为埋点属性。

## 12. 实施边界与预计文件影响

预计只在现有深度分析边界内修改：

- 题库配置、答案规范化、条件分支、摘要生成与会话状态；
- `/explore` 下的介绍、问卷、摘要、支付衔接与 Loading；
- 专项报告请求 Schema、固定分析顺序、职业报告 Prompt 和市场证据适配；
- `/deep-report` 的新职业报告渲染与旧报告只读兼容；
- 相关单元、组件、API、响应式与可访问性测试；
- README 中的当前用户路径、市场数据边界和恢复说明。

明确不在范围内：

- `lib/gemini/prompt.ts`；
- `lib/bazi/**`；
- `lib/validation.ts` 中的出生信息 Schema；
- `components/birth-form.tsx`；

## 13. 验证策略

实施使用测试驱动开发，每个新行为先以失败测试固定。

### 13.1 功能与数据

- 题库完整性、唯一 ID、选项与条件配置有效。
- 单选、多选、最多 3 项、互斥选项、其他文本和必填验证。
- 条件题的显示、隐藏与旧答案剔除。
- 返回修改、刷新恢复、会话损坏和版本升级。
- 现实条件摘要的准确转换与返回修改。
- API payload 严格验证、额外字段拒绝、空值、区间枚举、JSON 序列化。
- 未支付不调用检索；无效支付凭证不调用检索或报告模型。
- 旧问卷版本、旧方向、旧自定义 API 和旧 payload 无法新建报告。
- 市场检索失败时生成降级报告，不伪造数据。
- 报告恢复不产生额外模型调用。

### 13.2 典型用户

- **Case A：** 刚毕业、无家庭责任、可全国迁移、收入要求低、可全职学习、职业资本少。不应被过度限制转型范围。
- **Case B：** 30–40 岁在职、有家庭和房贷责任、不能换城市、最多降薪 20%、每周 5 小时、有多年行业经验。应明显优先邻近转型和可迁移资本。
- **Case C：** 待业、3 个月内需要收入、缓冲期短、愿意学习但无法长期无收入。应优先更快进入市场的邻近方向。
- **Case D：** 自由职业、可接受收入波动、地点自由、重视个人资产且不接受大型组织。排序应与 Case B 明显不同。

### 13.3 UI、可访问性与回归

- 测试 375px、390px、430px 和桌面端，不出现横向溢出、被浏览器工具栏遮挡或不可达操作。
- 点击区域、对比度、focus、键盘操作、ARIA、错误信息与不只依赖颜色的选中状态。
- 生成 Loading 仅显示真实阶段，减少动效时仍可读。
- 原有基础报告生成、基础报告渲染、反馈、支付、支付恢复和旧报告只读渲染不回归。
- 最终运行 TypeScript、ESLint、全量 Vitest 和 production build；任何失败必须按测试名称如实报告。

## 14. 验收与非目标

这一版成功的标志不是「题目更多」，而是同一份基础报告在四组现实条件下得到显著不同的候选排序，并且每个方向都有可执行的最低成本验证。

本次不承诺：

- 基于全国全量招聘数据的精确岗位数、薪资中位数或趋势时序；
- 替用户做最终职业决策；
- 提供录用保证、收入保证或「唯一正确职业」；
- 用职业专项的现实信息重写用户的基础报告。
